# Negative controls: MTP execution avoids generated test apphosts

Goal: `13630c9f`

During the 2026-08-27 acceptance run, the operator observed a visible
`Mcg.AgentOrchestrator.Infrastructure.Tests.exe` `0xc0000142` dialog. A nested focused-test
apphost under `Temp\Low\...\focused-artifacts` ran in the same interval, but Windows did not
retain evidence that identifies the dialog owner by full path. The apphost association therefore
remains a strong hypothesis, not a proven attribution.

The RED arm changed the focused-runner happy-path test to require the executed command receipt to
name `dotnet` while production still launched `$reuse.ExecutablePath` directly.

- Command: popup-suppressed MTP run filtered to
  `FocusedRunner_Pass_ExecutesUnderLeaseAndWritesReceipt`.
- Result: 1 executed, 0 passed, 1 failed.
- Expected failure: `Assert.Equal() Failure: Strings differ`; expected `"dotnet"`, actual a
  generated apphost path under `C:\Users\miles\AppData\Local\Temp\Low\...`.
- Scope: this proves the test goes RED when focused reuse still selects the generated apphost. It
  does not claim to reproduce `0xc0000142`; the wrapper intentionally suppressed Windows error UI.

The GREEN arm changed focused reuse to execute `dotnet <validated test assembly>` and record the
complete command arguments. The apphost remains a required build-artifact invariant.

- Happy-path command receipt: 1 executed, 1 passed; the receipt identified `dotnet.exe`, placed the
  expected test assembly at argument zero, recorded exit code 0, and contained a nonempty TRX.
- Receipt/source ordering contract: 1 executed, 1 passed.
- Budget and exact-tree termination path: 1 executed, 1 passed in 16.2 seconds; no dialog appeared.
- Complete focused-runner class: 19 executed, 19 passed in 21.7 seconds.
- Source-size ratchets: 15 executed, 15 passed.

The budget test deliberately does not assert a readiness marker produced inside its timeout
window. `docs/test-design-discipline.md` records that exact assertion as a prior host-speed race;
execution authority instead comes from the separate happy-path receipt and TRX assertions.

The goal later expanded the same invariant to acceptance and stable-slot MTP execution. The
acceptance manifest still declares and validates the generated apphost as a build artifact, but the
gate resolves the corresponding managed `.dll` and executes `dotnet <managed assembly>`. Focused
evidence and `stable-slot-dotnet mtp-test` do the same. This changes the acceptance root command; the
earlier statement that it remained unchanged was superseded and was false for the final patch.
Because manifest identity participates in the partition verdict cache key, the manifest and lane
changes intentionally invalidate prior partition-reuse keys. Direct inspection of the two latest
stored acceptance events for this goal found `partitionReuseAttemptCount` was null in both, so there
is no recorded reuse attempt for this goal that the new identity discards.

## Lock-attribution negative control

The historical dotnet-host change had been reverted because
`LockAttribution_restart_manager_names_file_holder` expected `Process.ProcessName`. Reapplying the
dotnet host without changing that presentation assertion produced 20 passed, 1 failed, 1 skipped:
Restart Manager remained the source, returned the exact holder PID and start time, and named the
holder `.NET Host` rather than `dotnet`. Receipt:
`focused-20260828T025355145-5c8538af.receipt.json`.

The corrected assertion derives the expected Restart Manager display name from the executable's
`FileDescription`, falling back to `ProcessName`. It now locks a unique temp file rather than probing
the machine-wide `dotnet.exe` image. The exact Restart Manager test passed in the combined GREEN
receipt `focused-20260828T041037151-164d3370.receipt.json` (25 passed, 1 unrelated skip).

## Stable-slot suppression negative control

With the stable runner launching `dotnet <managed assembly>`, an interactive one-variable experiment
observed that the general-purpose hidden-console suppression path printed a green MTP summary and
then returned exit 1 before the test assembly's process-exit diagnostics. Changing only that launch
to ordinary `Process.Start` returned 0. Holding the hidden-console scope until process exit still
returned 1. Error-mode-only suppression (`SEM_FAILCRITICALERRORS`, `SEM_NOGPFAULTERRORBOX`, and
`SEM_NOOPENFILEERRORBOX`) with `CreateNoWindow=true` returned 0 and retained normal process-exit
output. The retained TRX files under `.scratch/stable-slot-clean-relative`,
`.scratch/stable-slot-process-start-control`, `.scratch/stable-slot-held-suppression`, and
`.scratch/stable-slot-error-mode-only` each prove 71/71 tests passed, but do not retain the outer
command exit code; those exit-code comparisons remain operator observations rather than durable
machine-verifiable receipts.

The error-mode inheritance test first clears those flags in the parent. With the production helper
temporarily stubbed to a no-op it went RED exactly at the in-scope error-mode assertion (3 passed,
1 failed): `focused-20260828T040945154-fc2db2ef.receipt.json`. Restoring the helper went GREEN and
also proved child inheritance, no hidden-console acquisition, and restoration of the cleared parent
baseline: `focused-20260828T041037151-164d3370.receipt.json`.

## Nested native `dotnet test` crash control

A later focused run still deliberately executed five generated test apphosts through nested SDK
`dotnet test --project` contract tests. All five contracts failed. The retained Dashboard output
identified one exact mechanism: the generated apphost exited `-532462766` (`0xe0434352`) after
`Microsoft.Testing.Platform.IPC.NamedPipeClient.ConnectAsync` threw
`UnauthorizedAccessException`; discovery then reported zero tests. The Infrastructure failure's
diagnostic tail was truncated by build warnings. A contemporaneous operator-observed
`Infrastructure.Tests.exe` `0xc0000142` dialog had already disappeared when inspected and produced
no Application/WER event, so it must not be conflated with the proved Dashboard exception.

Removing only `AcquireErrorModeForChildSpawn` from the nested process helper did not change the
result: both large-project native-apphost cases still failed. Receipt
`focused-20260828T042536677-9224d5fc.receipt.json` records 0 passed / 2 failed. This exonerates the
error-mode wrapper as the cause; removing it would expose Windows error UI without repairing MTP.

Those contracts now match the production seam. Each case performs an isolated build, asserts that
both the generated apphost and managed test assembly exist, and executes
`dotnet <managed test assembly>` with a nonzero minimum test count. The two large projects passed
2/2 in `focused-20260828T043342070-5feea20d.receipt.json`. The complete MTP runner/script seam then
passed 35/35 in `focused-20260828T050813741-b0f1af3b.receipt.json`; its receipt confirms the outer
executable was `C:\Program Files\dotnet\dotnet.exe` and argument zero was the managed
Infrastructure test assembly.

Post-review verification added the previously missing `{executableExtension}` token to the real
focused-evidence fixture. The entire focused-evidence class passed 39/39 in
`focused-20260828T050159548-67922e1c.receipt.json`. The strengthened no-rebuild shard invariant
passed 6/6 in `focused-20260828T050323842-3764ec33.receipt.json`. The final manifest/settings and
error-mode suppression set passed 38/38 in
`focused-20260828T050738742-f1b7ed2c.receipt.json`.

## Self-host acceptance limit

Popup-suppressed acceptance attempt
`13630c9f-gate-20260828054059288-cd3b361884c748e5a3197ed4c7d3c327` was launched by the existing
mainline verifier at `0d44d054`, not by the candidate gate implementation. Elevated process capture
proved that verifier started six top-level
`Mcg.AgentOrchestrator.Infrastructure.Tests.exe` shard apphosts from the goal artifact root, with
the expected lane filters and TRX arguments. The exact acceptance root PID 32116 was stopped after
capture; all six apphosts had exited and no test apphost remained. This attempt is inconclusive for
the candidate: a gate change cannot validate its own launch behavior until it lands. The patch must
land alone and the conductor must restart on the new mainline binary before post-landing acceptance
can establish the full-suite process shape.

## Scope limit

These controls prove that the acceptance/focused/stable **top-level** MTP commands no longer name an
`Infrastructure.Tests.exe` apphost. The default `scripts/MtpTestRunner.psm1` path and the repository
contract tests now also execute managed assemblies with `dotnet`; an explicitly supplied custom
`RunnerPath` remains an intentional arbitrary-runner seam. Manual SDK `dotnet test --project` can
still execute a generated apphost, but no automated acceptance lane in this patch relies on it.
These controls do not prove the operator-observed dialog's full-path owner. Another dialog would
still require a process-tree capture; absence of a dialog is not an acceptance criterion.
