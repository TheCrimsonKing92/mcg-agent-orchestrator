# Task-intent dispatch admission verification

Status: implementation and build evidence only. Automated execution belongs to Acceptance; live observation and independent different-family review remain prospective.

The intent inbox owns the task hold: Pending and Claimed task-targeting rows protect dispatch until their terminal transition. Enqueue inserts the row and advances its task admission revision in one transaction. Duplicate submissions retain the original five-minute deadline. The conductor checks for a persisted application receipt before rejecting an expired request, so a crash between goal persistence and inbox completion does not repeat the effect.

Prepared revisions are persisted independently of goal-row versions. Selection excludes only held tasks. Enqueue and final child creation use the same task-scoped named mutex; the host checks the durable preparation, persists any suppression, and retains serialization through child creation and start acknowledgement. Optional samples carry the same task admission identity. Suppressed hosts exit with a distinct native outcome and are reconciled without a failed verification or a paid retry charge. Store/synchronization failures deny launch; an abandoned scope requires owned-process recovery before another launch attempt.

Acceptance must execute `TaskIntentDispatchAdmissionTests`, `DispatchProcessHostIntentAdmissionTests`, `OperatorIntentStoreTests`, `StoreSchemaRegistryTests`, `OperatorIntentCoordinatorTerminalCompletionTests`, `ConductorBatchLoopTestsOperatorIntents`, `ConductorBatchLoopTestsOperatorIntentBatch`, `CliCommandTestsPersistentRunnerCommandsLateIntent`, `RetryAdmissionReservationStoreTests`, `WorkerDispatchTestsRetryStartGoalEvents`, `OperatorIntentGoalApplicationOfflineTests`, and `CliCancelDispatchIntentOrderingTests` on the candidate. The late-enqueue control must fail when final host admission is disabled: the unpaid probe writes its child-start marker and exits normally instead of producing a suppression. Compile errors, zero selected tests, and timeouts do not satisfy that control.

Before live observation, publish/relaunch the candidate using the [operator runbook](../operator-runbook.md) and record the loaded candidate identity. The live check uses an isolated disposable goal, an unpaid probe, and the normal CLI/conductor boundary:

1. Prepare the probe and pause its start gate and intent application. Submit `verify-manual`, `retry`, or `progress`; retain the returned Pending intent ID and exact candidate.
2. Let selection and the prepared host proceed while application remains paused. Confirm no probe child starts. Reload the durable `task_intent_suppressions` receipt and check goal ID, task ID, intent ID, verb, prepared version, and current task version.
3. Resume application and poll `operator-intent-status <intent-id>` through the repository CLI wrapper. Confirm one terminal intent transition and one task effect after restart.
4. Repeat with another task in the same goal and a task in another goal; both unpaid probes must start. Reject a stale target intent, prepare a fresh attempt, and confirm it can start.
5. Restart after enqueue, after claim, and after persisted effect. Advance an injected clock for expiry in automated coverage; confirm expired unapplied requests become Rejected and never apply later.
