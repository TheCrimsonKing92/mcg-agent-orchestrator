## Conditional ownership negative control

No complete-override ownership guard is added by this goal slice. Such a repair
is authorized only after a current-head stable-slot receipt identifies a
same-process hook leak as the cause. The diagnostic path still captures the five
hook values once at invocation entry and passes that immutable snapshot through
the selected attribution path; it does not change legacy setter behavior.

The currently authorized restoration control is
`LockAttributionClearedOverrideRestoresTimeoutBranch`: it clears every legacy
hook in `finally`, asserts all five defaults before the next invocation, and
requires that the next diagnostic snapshot reach the timeout branch. This
guards the diagnostic matrix against a retained empty override without claiming
that a global owner existed historically.

If a causal receipt later authorizes an ownership repair, acceptance must add a
RED/GREEN control proving that replacement, partial clearing, or stale
restoration is possible with the guard bypassed and rejected with the guard
restored. Until that receipt exists, implementing that guard would be a guessed
global hook redesign.

The Developer role is restricted to the sanctioned build check, so it cannot
produce either runtime receipt. Acceptance owns the focused matrix, RED/GREEN
negative-control execution if causally authorized, the complete `Dotnet build
slots` partition, and current-head TRX hashes.
