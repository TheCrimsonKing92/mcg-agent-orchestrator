# Negative control: the retained-capture-incomplete message must name the process holding the log

Goal `09740603` lands holder-identity diagnostics for the post-landing canary's retained captures. The
whole point of the change is one added fact in
`tests/Mcg.AgentOrchestrator.Infrastructure.Tests/PostLandingCanaryCaptureAvailabilityTests.cs`,
`RunProcess_UnrelatedRedirectedSpawnInLaunchWindowIsReportedIncompleteNamingHolder`, which starts an
unrelated redirected child inside the canary launch's inheritance window through the per-launch
`inheritableWindowObserver` hook and asserts that the runner still throws `retained-capture-incomplete`
*and* that the message names that child's process id.

That fact is only worth anything if it fails when the holder naming is removed. Everything else in the
message (`exclusive-open`, `job-exit-confirmed`) was already provable before this goal, so a fact that
still passes with `capture-holders` deleted would be asserting on the old behaviour and not on the new.

## Mutation

In `src/Mcg.AgentOrchestrator.App/Orchestration/PostLandingCanaryRunner.cs`, inside
`EnsureRetainedCaptureReadable`, delete exactly the one interpolated segment that names the holders from
the thrown message:

```csharp
            $"capture-holders={holders.Format()}; " +
```

so the `throw new InvalidOperationException(...)` argument becomes

```csharp
            $"surviving-descendants={FormatProcessIds(survivingDescendantProcessIds)}; " +
            $"stable-length={FormatStableLength(observation)}");
```

Nothing else changes: `FileHandleHolders` still lands, the holder read on the failure path still runs,
`EnsureRetainedCaptureReadable` still throws on every refused exclusive open, and every other key in the
message is untouched. The mutation removes only the naming, which is the single behaviour this goal adds
to the failure path.


`IncompleteCapture_ReportsReleaseAndAvailabilityEvidence` fails alongside it on the same missing key,
which is the expected second signal and not a separate defect.
