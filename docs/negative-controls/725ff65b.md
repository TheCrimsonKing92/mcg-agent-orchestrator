# Windows MTP startup-hook cache path controls

The reproduced failure is Windows PowerShell 5.1 resolving a complete cache through ordinary filesystem APIs once the public assembly path reaches 264 characters. The fix uses extended paths for cache I/O and a bounded, owned compiler directory; the returned assembly path and caller TEMP/TMP remain ordinary and unchanged.

Operator evidence is retained under `.orchestrator/operator-evidence/rearchitecture-20260906/` in the driving repository. These are focused receipts, not a full acceptance verdict.

`MtpTestRunnerScriptTests.RepositoryRoot` derives its root from `CallerFilePath`.
Copying its DLL and setting a different invocation root does not redirect the
fixture's implicit module reads. A first attempted rename negative control changed
the invocation checkout and passed because it did not load the mutation; that run
is inconclusive and explicitly marked invalid as a negative control. The subsequent
explicit-module control above is the actual RED evidence.

Two broader 52-test runs produced passing execution receipts, but their frozen
assemblies and assumed isolated source locations were not sufficient to establish
which module bytes every fixture consumed. Their receipts are qualified and must
not be presented as final validation of this amended candidate. The ten focused
controls above ran against their actual compile-time source checkout; the cold
script controls imported the module explicitly. Native Reviewer and full acceptance
remain required before landing.
