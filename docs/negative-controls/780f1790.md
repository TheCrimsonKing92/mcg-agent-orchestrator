# Acceptance gate scheduler negative controls: 780f1790

Date: 2026-08-09

This goal changes admission so a shard whose exclusive resource is busy cannot occupy an execution slot,
and refreshes all 18 lane estimates from the clean `a9920536` receipt. The following controls were
deliberately left unchanged:

No exclusive resource key was removed. Retention preserves the existing isolation contract while the
required repeated real-process evidence is absent. The evidence for each retained key is:

| Retained key | Evidence for retention |
| --- | --- |
| `xunit:GoalWorktreeCleanupHooks` | The slot root is GUID-isolated, but the former partner lanes lack 50-100 clean overlapping real-process runs in a disposable worktree under representative host load, covering every member, released lease, and cleanup target. |
| `xunit:EnvMutation` | Environment variables are process-local, but complete lane membership lacks the same 50-100-iteration receipt clearing fixed paths, ports, stores, and named OS resources. |
| `xunit:ProcessSpawning` | Process creation alone is not shared state, but 50-100 representative-load real-process runs have not proven registry, endpoint, launcher-file, handle, and child cleanup. |
| `xunit:DotnetBuildSlots` | Source shows a run-scoped root override, but 50-100 disposable-worktree overlap runs have not proven fallback behavior and subprocess inheritance across both lanes. |
| `xunit:JobAccounting` | Job handles are normally process-owned and repositories are uniquely seeded, but 50-100 representative-load partner-lane child-exit, PID, and slot-lease cleanup receipts are absent. |
| `xunit:GoalAcceptanceVerifier` | Static hooks are process-local, but 50-100 disposable-worktree concurrent runs have not proven nested subprocess root inheritance and cleanup across the verifier/remainder filters. |

The complete source boundaries and required receipts are recorded in
`docs/acceptance-gate-resource-isolation.md`.
- `ChaosGateGit` and `ProviderEnvironment` remain unkeyed. Their audited identities are respectively
  per-test GUID repositories and process-local environment plus OS-assigned loopback ports. Adding a key to
  a collection that occupies one lane would not create cross-lane serialization.
- Lane filters, the 18-lane count, gating verdicts, `maxConcurrentShards`, and `slotCount` were not reduced
  or tuned. The change is scheduling-only; it does not run fewer tests or admit more shards.
- Worker admission, build-slot capacity, parallel-goal capacity, and dashboard capacity surfaces were not
  changed because they are separate limits and outside this goal.
- No worker-generated post-change wall-clock result is recorded. The acceptance workflow owns that receipt;
  `docs/acceptance-gate-resource-isolation.md` records the baseline, exact comparison method, and bounded
  prediction without presenting an unrun measurement as evidence.

Because no key was removed, this change does not claim the former partner lanes are safe to overlap. A
future change may remove at most one key and must first run that pair concurrently for 50-100 clean
real-process iterations in a disposable worktree under representative host load. Any flake retains the key.
Only then may it run a full 18-shard gate with nonzero counts, complete TRX receipts, all gating verdicts,
and no leaked repository, environment, process, port, slot, job, or filesystem state.
