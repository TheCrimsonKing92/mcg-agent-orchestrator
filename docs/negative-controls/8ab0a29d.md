# Negative control: native MTP `dotnet test` opt-in

Goal `8ab0a29d` enables the .NET 10 native Microsoft.Testing.Platform test driver through
`global.json`. `TestingPlatformDotnetTestSupport` is intentionally absent: it was the .NET 9 / MTP
v1 compatibility bridge and MTP v2 rejects that VSTest-based path on .NET 10.

To verify the negative control in a disposable checkout:

1. Remove the top-level `test` object from `global.json` without changing the SDK selection.
2. Run `dotnet test tests/Mcg.AgentOrchestrator.Core.Tests/Mcg.AgentOrchestrator.Core.Tests.csproj --filter FullyQualifiedName~RepositoryChangeClassifierTests` and retain the complete command output and exit code.
3. Confirm the command fails with `Testing with VSTest target is no longer supported by Microsoft.Testing.Platform on .NET 10 SDK and later`.
4. Restore `global.json`, rerun the same command, and confirm the selected tests pass.

The subscription Developer lane may compile but may not execute test hosts. The acceptance/operator
lane owns the all-project positive and negative receipts;
`MtpTestRunnerScriptTests.NativeMtpDotnetTestRunsARepositoryProjectInOneStep` keeps a representative
one-step invocation in the repository gate.

## Operator execution, 2026-08-14 — the opt-in works, one-step still does not

The Developer's blocker is confirmed and is a real technical finding, not an evidence-routing gap. The
`global.json` opt-in is necessary and demonstrably active, but it is **not sufficient**: one-step
`dotnet test` still fails in this repository.

### The procedure above is not executable as written

Steps 2 and 4 specify VSTest-era invocation that the native driver rejects:

    dotnet test tests/....csproj --filter FullyQualifiedName~RepositoryChangeClassifierTests
      -> "Specifying a project for 'dotnet test' should be via '--project'."

Both the positional project path and `--filter` are the old shape. The procedure was written in the
vocabulary of the thing this goal replaces, by an author who could not execute it. Corrected commands are
below.

### RED — opt-in removed (control state)

`global.json` `test` object removed, run from the repository root:

    dotnet test tests\Mcg.AgentOrchestrator.Core.Tests\Mcg.AgentOrchestrator.Core.Tests.csproj
      --filter FullyQualifiedName~RepositoryChangeClassifierTests

    Microsoft.Testing.Platform.MSBuild.targets(263,5): error : Testing with VSTest target is no
    longer supported by Microsoft.Testing.Platform on .NET 10 SDK and later.   exit 1

That is the documented expected failure, and it confirms the SDK hard-rejects the VSTest path on .NET 10 —
which is why the two-phase build-then-launch-apphost wrapper exists.

**Method note:** an earlier attempt at this control was invalid and is recorded here deliberately. The
mutation was made in the goal worktree while the command ran from the main repository root. `global.json`
resolves from the *current directory*, not from the project path, so both arms read main's `global.json` and
produced identical output. A control whose arms agree is not a control. Run every arm from the worktree.

### GREEN — opt-in present: driver active, run still fails

Restored `global.json`, run from the goal worktree. The driver is unambiguously active — native project
syntax is enforced, MTP exit codes and summary format appear — but no test executes:

    dotnet test --project tests\...\Core.Tests.csproj
      -> Zero tests ran, Exit code: 5 (InvalidCommandLine), duration 223ms
         stderr: assembly-temp-redirect selected=...\Temp\Low\mcg-tests rejected=<none>

Exit 5 reproduces with no filter arguments at all, so it is not filter syntax. The apphost rejects what the
SDK driver passes it.

### The isolated-artifacts comparison the blocker asked for

Same command, with and without a unique `--artifacts-path`:

    without --artifacts-path   Unhandled exception. System.UnauthorizedAccessException:
                               Access to the path is denied.
                                 at Microsoft.Testing.Platform.Hosts.TestHostBuilder.BuildAsync(...)

    with    --artifacts-path   no access exception; Zero tests ran, exit 5 InvalidCommandLine

So a unique artifacts path **does** eliminate the access denial — the isolated root is load-bearing — but it
does not make the invocation succeed. Two distinct failures, one masked behind the other.

Note the `assembly-temp-redirect` from `7b856497` selects `Temp\Low\mcg-tests` and reports
`rejected=<none>` in **both** arms, so that redirect is working and is not the cause.

### What this means for the goal

The brief's premise — "the fix is a single MSBuild opt-in that is currently set nowhere" — does not hold. The
opt-in is correct and necessary; something in how the SDK driver invokes this repository's apphosts is
rejected at the command-line layer. Recommended next step is to capture the exact argument vector the driver
passes (MTP diagnostic logging) and compare it against what `Invoke-IsolatedDotnet.ps1` passes today, since
the latter works.
