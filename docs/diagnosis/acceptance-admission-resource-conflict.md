# Acceptance-admission diagnosis

Source snapshot: `871dde49769680430cad2fd1e5b0eaad385623b6` (read on 2026-08-22 UTC). The diagnosis is for the ordinary parallel-acceptance fallback used by these receipts: the cohort selector emitted `outcome=unpaired ... fallback=ordinary` immediately before the ordinary starts/holds (`.orchestrator/logs/conduct-events.log:6-12`).

## Bottom line

**Fact.** A second fully verified goal does not merely need one of the two .NET build permits to be free. Before the ordinary conductor will launch its acceptance attempt, it must survive the ordered readiness/circuit/fairness checks, fit under the in-memory logical acceptance width, have no live evidence-mutation lease for that same goal, and have no serialized ownership key or non-documentation landing path that overlaps an earlier active acceptance candidate. Only after the conductor emits `ACCEPTANCE ... result=started` does the child scan for a physical `build-0` or `build-1` execution permit (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorBatchLoop.cs:2949-3124`; `src/Mcg.AgentOrchestrator.App/Orchestration/ConductorParallelAcceptanceAttempts.cs:1064-1101,1207-1263`).

**Fact.** In the `6b0589b8` case, the binding resource was the serialized repository-ownership key `ownership:test-project:tests/mcg.agentorchestrator.infrastructure.tests`, already reserved by active candidate `b545208f`. The same-tick speculative receipt says exactly `6b0589b8:SerializedResourceOverlap(conflict=b545208f,resource=ownership:test-project:tests/mcg.agentorchestrator.infrastructure.tests)` (`.orchestrator/logs/conduct-events.log:6`). This key is created because both write sets contain files under `tests/Mcg.AgentOrchestrator.Infrastructure.Tests`; the attempt scopes show `b545208f` test files at `.orchestrator/acceptance-gate-attempts/b545208f69bc4d2280f2148cdc728f02/b545208f-0-20260822001631061-e5bcfb30450045c7b2a4cf6e218787b8.attempt.json:23-24` and `6b0589b8` test files at `.orchestrator/acceptance-gate-attempts/6b0589b8724c4f5381f396af3855586b/6b0589b8-0-20260822003323986-3a9a3257a9db4c11afcdaeb4e322266d.attempt.json:21-22`. Test paths are grouped by their second path segment into a serialized test-project reservation (`src/Mcg.AgentOrchestrator.Core/Application/RepositoryOwnershipMap.cs:35,111-116,178-192,211-224`), then prefixed with `ownership:` (`src/Mcg.AgentOrchestrator.Core/Application/RepositoryLandingScopeNormalization.cs:42-58`).

**Inference, strongly supported but not encoded in the generic hold itself.** The ordinary `activeCandidates.Any(existing => existing.Overlaps(candidate))` branch bound on that shared key, not merely an overlapping filename. The ordinary hold record only says `parallel acceptance resource conflict`; it does not record the discriminating path/key (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorBatchLoop.cs:3106-3114`). The exact key is recoverable here because the separate same-tick speculative projection records it and the persisted scopes independently reproduce it. Without that projection/scope evidence, the generic hold alone would establish only “shared resource key or overlapping non-doc path,” because `Overlaps` tests those two alternatives (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorParallelAcceptance.cs:19-27`).

## 1. Precise ordinary-admission path

The checks below are in execution order. A failure `continue`s the loop, so a later predicate is not evaluated and only the first binding reason is visible.

1. **Fact — eligibility set.** The batch first retains goals whose acceptance lifecycle is eligible, whose status is `Verified` or `Verifying`, whose tasks are all cancelled or completed with a passed last verification, whose dependencies are not held, and which have no unresolved persisted Verified-stage acceptance escalation (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorBatchLoop.cs:2659-2666,3548-3553,4689-4732`). Lifecycle eligibility reads the goal operation journal and excludes retired/merge-evidence terminal dispositions (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorBatchLoop.cs:3505-3528`). Goals are ordered by their derived Verified time, then first timeline event, then ID (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorBatchLoop.cs:3460-3465,3531-3545`).

2. **Fact — durable attempt reconciliation and fresh verification/circuit checks.** Existing unreconciled attempt JSON is observed before new admission; the coordinator enumerates `*.attempt.json` and reads canonical metadata (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorBatchLoop.cs:2671-2728`; `src/Mcg.AgentOrchestrator.App/Orchestration/ConductorParallelAcceptanceAttempts.cs:378-407`). In the ordinary loop the authoritative `kernel.BuildVerificationGate(goal.Id)` must still be satisfied, then the acceptance-engine circuit read must not require a hold (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorBatchLoop.cs:2949-2981`). These read kernel task-verification state and circuit state, respectively; they are not capacity checks.

3. **Fact — configured logical width must be valid.** `driver.GetAcceptanceSlotCount(goal)` must be in `[1, trustedHostSlotCount]` (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorBatchLoop.cs:2984-3005`). In production the public driver constructor fixes that getter to `DefaultParallelAcceptanceCapacity` (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorDriver.cs:239-247`), and the default is `DotnetBuildEnvironmentManager.BuildConcurrencySlotCount`, currently 2 (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorBatchLoop.cs:43-47`; `src/Mcg.AgentOrchestrator.Infrastructure/Workspaces/DotnetBuildEnvironmentManager.cs:86-96`). This is logical admission width, not proof that a physical permit is currently held or free.

4. **Fact — fairness runs before capacity and overlap.** For a goal with no live attempt, if it is newer than the oldest non-live waiter, the oldest has not yet been served in this tick, and the process-local overtake counter has reached 1, the goal is held with `parallel acceptance fairness waiting for oldest verified goal ...` unless the oldest-waiter stall bypass applies (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorBatchLoop.cs:3008-3055,3584-3596`). The oldest waiter is selected after excluding goals with live attempts (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorBatchLoop.cs:3467-3502`); live-attempt identity comes from the latest attempt JSON (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorParallelAcceptanceAttempts.cs:755-778,1746-1763`). The fairness counters are static in-process state, not a build-lock or repository-resource lease (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorBatchLoop.cs:3584-3633`).

5. **Fact — per-candidate logical slot count.** `activeCandidates.Count` must be below `acceptanceSlotCount`; otherwise the goal is held as `candidate manifest slot cap ... reached` (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorBatchLoop.cs:3057-3067`). `activeCandidates` is a current-tick in-memory list, populated when an earlier ordered candidate's attempt decision is `Started` or `Running` (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorBatchLoop.cs:3134-3237`). It does not inspect OS lock files.

6. **Fact — candidate construction.** The policy must permit the Verified transition; resolved lifecycle must still be `Verified`/`Verifying`; all tasks must still have completed/pass evidence; and, for a goal without a live attempt, no unexpired goal-evidence mutation lease may exist. The slot index must also be in range (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorDriver.cs:3075-3115`). The evidence lease is read from `ReconcileSweepRemediationStore` over `workspace.SqliteStatePath` and considered active only until its `ExpiresAtUtc` (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorDriver.cs:276-289,5519-5528`). The candidate's file scopes come from changed files in the goal worktree, with task-text inference only if the observed change set is empty (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorDriver.cs:923-932,5878-5895`). Normalization excludes `docs/**` and `*.md` from conflict paths, creates serialized ownership keys, and reserves a special unknown-scope key if no scope exists (`src/Mcg.AgentOrchestrator.Core/Application/RepositoryLandingScopeNormalization.cs:11-39,42-67`; `src/Mcg.AgentOrchestrator.App/Orchestration/ConductorParallelAcceptance.cs:48-67`).

7. **Fact — host logical cap, then cross-goal conflict.** The code next repeats a host-cap check and then rejects the candidate if any earlier active candidate shares a serialized `ResourceKey` or has an exact/directory-prefix overlap among non-doc conflict paths (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorBatchLoop.cs:3094-3114`; `src/Mcg.AgentOrchestrator.App/Orchestration/ConductorParallelAcceptance.cs:19-27`; `src/Mcg.AgentOrchestrator.Core/Application/RepositoryPathOverlap.cs:12-32`). This is the branch that held `6b0589b8`.

8. **Fact — launch precedes physical permit acquisition.** Only after those checks does `ParallelAcceptanceAttemptCoordinator.Evaluate` persist/launch an attempt and return `Started` (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorBatchLoop.cs:3121-3213`; `src/Mcg.AgentOrchestrator.App/Orchestration/ConductorParallelAcceptanceAttempts.cs:838-900`). The child first runs the already-merged pre-slot shortcut, then scans all `BuildConcurrencySlotCount` execution-lock files for a permit for up to 20 seconds (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorParallelAcceptanceAttempts.cs:1064-1101,1207-1263`; `src/Mcg.AgentOrchestrator.Infrastructure/Workspaces/DotnetBuildEnvironmentManager.cs:746-826`). Therefore a build-permit failure necessarily has a started attempt plus `ACCEPTANCE_LEASE_WAIT/YIELD` evidence; it cannot produce only the pre-launch `parallel acceptance resource conflict` hold.

**Fact — orthogonal worker accounting.** `ConductorDriver.GetWorkerAdmissionSnapshot` reserves one unit from the paid-worker pool when `_hasGateReadyGoal()` is true (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorDriver.cs:214-225`). That `reservedGateSlots` field changes the paid-worker cap; `RunParallelAcceptanceBatch` does not read it. It is not a physical build permit and did not bind this case.

## 2. What bound for `6b0589b8`, and how the records discriminate it

**Fact.** At tick 166, the speculative projection explicitly classified `6b0589b8` versus `b545208f` as `SerializedResourceOverlap` on `ownership:test-project:tests/mcg.agentorchestrator.infrastructure.tests`; the ordinary cohort path then fell back, `b545208f` started, and `6b0589b8` was held for `parallel_acceptance_resource_conflict` (`.orchestrator/logs/conduct-events.log:6-12`). The speculative classifier returns a named serialized resource when the two normalized `ResourceKeys` intersect (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorParallelAcceptance.cs:292-327`), and its projection obtains each worktree's changed files against HEAD and normalizes them (`src/Mcg.AgentOrchestrator.App/Orchestration/GateReadyCandidateProjector.cs:23-49,80-103,143-152`).

**Fact.** It was not logical-slot exhaustion: capacity is 2, only one active gate is shown, and the emitted goal reason is resource conflict rather than `candidate manifest slot cap 2 reached` or `parallel acceptance slot cap reached` (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorBatchLoop.cs:3057-3065,3094-3103,3106-3113`).

**Fact.** It was not physical build-permit exhaustion. `6b0589b8` had no `ACCEPTANCE ... started`, no lease wait/yield, and no gate progress in the stated window. Meanwhile `b545208f` acquired `build-0` at 00:17:23 and released the execution lock at 00:18:09 (`.orchestrator/logs/conduct-events.log:17,24`). Despite that physical permit becoming free, `6b0589b8` did not start until 00:33:24, immediately after `b545208f`'s end-of-attempt lease release/pass at 00:33:24 (`.orchestrator/logs/conduct-events.log:192-194`). This timing matches a full-attempt logical ownership reservation, not a prebuild-only build lock.

**Fact.** A physical-permit block has distinguishable records: acquisition emits `ACCEPTANCE_LEASE_WAIT`, timeout emits `ACCEPTANCE_LEASE_YIELD ... waitReason=all-permits-busy`, and throws `DotnetBuildSlotsBusyException` (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorParallelAcceptanceAttempts.cs:1217-1263,1314-1369`). The supplied goal has none. A logical slot cap is also distinct via its held reason and the aggregate `ADMISSION ... reason=parallel-acceptance-slot-cap` record (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorBatchLoop.cs:3057-3066,3093-3103,3293-3297`).

## 3. Fairness versus resource conflict

**Fact.** They are independent predicates in one ordered admission path, not two labels for one test. Fairness reads oldest-waiter identity and process-local bounded-overtake/stall counters and runs first (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorBatchLoop.cs:3008-3055,3472-3502,3584-3596`). Resource conflict runs later and reads the normalized scopes/ownership keys of candidates already active in this tick (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorBatchLoop.cs:3069-3124`; `src/Mcg.AgentOrchestrator.App/Orchestration/ConductorParallelAcceptance.cs:19-27`). Because the fairness branch `continue`s, it can mask a conflict on a tick; when fairness no longer defers, the same goal can reach the later overlap check. That explains `7135991f` alternating between reasons without implying that a single resource changed.

**Fact.** Operators distinguish them from the goal hold: fairness names the oldest goal and also emits `ADMISSION ... result=deferred reason=parallel-acceptance-fairness` (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorBatchLoop.cs:3021-3050`); resource conflict emits the generic `GOAL ... reason=parallel_acceptance_resource_conflict` from the later branch and no dedicated ordinary `ADMISSION` detail (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorBatchLoop.cs:3106-3114`). To identify the exact resource, consult the same-tick `SPECULATIVE_COHORT_PLAN` record, which formats `SerializedResourceOverlap(...,resource=...)` (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorParallelAcceptance.cs:192-197,320-327`). For `7135991f`, rotated receipts likewise name the same Infrastructure-tests project key (`.orchestrator/logs/conduct-events-20260821180139.log:873,880,883,887,891,897,1140,1203`).

**Fact.** In the simplified `b545208f`-running/`6b0589b8`-only-waiter situation, fairness cannot be the blocker: live attempts are excluded from oldest-waiter selection, so `6b0589b8` is the oldest non-live waiter, while the fairness condition requires `goal.Id != oldestWaiter.Id` (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorBatchLoop.cs:3009-3013,3467-3470`). The resource-conflict record is therefore consistent with both the control flow and the exact overlap receipt.

## 4. What a running gate holds over time

**Fact — full attempt.** A running gate occupies one logical `activeCandidates` position and makes its normalized `ResourceKeys`/`ConflictScopePaths` conflict with later candidates for every tick in which its attempt remains `Started`/`Running` (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorBatchLoop.cs:3134-3237`). It also holds a goal-keyed evidence-mutation lease across rebase and verification, disposed when `RunParallelLandingAcceptance` returns (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorDriver.cs:3951-4007`). The evidence lease protects that goal's evidence; the cross-goal serialization in this case comes from `activeCandidates.Overlaps`, not from the goal-keyed SQLite lease.

**Fact — prebuild only.** The child acquires any free physical build permit, not necessarily the logical `candidate.SlotIndex`, by scanning both permit lock paths (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorParallelAcceptanceAttempts.cs:1207-1246`; `src/Mcg.AgentOrchestrator.Infrastructure/Workspaces/DotnetBuildEnvironmentManager.cs:755-806`). For MTP infrastructure shards, the verifier performs the shared prebuild, verifies the executables, then explicitly calls `primaryLease.ReleaseExecutionLock()` before scheduling shards (`src/Mcg.AgentOrchestrator.Infrastructure/Workspaces/GoalAcceptanceVerifier.cs:1218-1246`). Releasing closes the execution-lock stream and flips `IsExecutionLockHeld`; a later `Dispose` is idempotent (`src/Mcg.AgentOrchestrator.Infrastructure/Workspaces/DotnetBuildEnvironmentManager.cs:2446-2529`).

**Fact — shard phase.** Shards reuse the prebuilt environment through `ShardWorkerLease`, but do not keep the build execution lock after the explicit release (`src/Mcg.AgentOrchestrator.Infrastructure/Workspaces/GoalAcceptanceVerifier.cs:1264-1284`). Their `ExclusiveResourceKeys` are a separate, intra-gate in-memory scheduler set: keys are added only while a shard is active and removed when that shard completes (`src/Mcg.AgentOrchestrator.Infrastructure/Workspaces/GoalAcceptanceVerifier.cs:1259-1261,1297-1357`). Those shard keys are not the cross-goal candidate ownership reservation.

**Fact — receipt semantics.** `ACCEPTANCE_LEASE_PERMIT_RELEASE ... releaseKind=execution-lock` is the authoritative physical-permit release. `ACCEPTANCE_LEASE_RELEASE` is emitted later when attempt custody ends and the lease object is disposed, even if its execution lock was already released (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorParallelAcceptanceAttempts.cs:1132-1152,1233-1245,1333-1344`). In this run: started 00:16:33; `build-0` acquired 00:17:23; execution lock released after 47,302 ms at 00:18:09; environment/custody released and gate passed at 00:33:24 (`.orchestrator/logs/conduct-events.log:10,17,24,192-193`). The logical ownership conflict therefore outlived the physical build lock by about 15 minutes.

## 5. Dead, redundant, or misleading admission code under current constants

**Fact — unreachable second cap.** For every value accepted by the validation, `acceptanceSlotCount <= trustedHostSlotCount`. Therefore if the earlier `activeCandidates.Count >= acceptanceSlotCount` check does not fire, the later `activeCandidates.Count >= trustedHostSlotCount` check cannot fire (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorBatchLoop.cs:2984-3005,3057-3067,3094-3104`). Under current production constants both are exactly 2, so the later `"parallel acceptance slot cap reached"` branch is redundant/unreachable. The aggregate `ADMISSION ... reason=parallel-acceptance-slot-cap` can still fire because `deferredByAdmission` is incremented by the earlier per-candidate-cap branch (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorBatchLoop.cs:3057-3060,3293-3297`).

**Fact — constant-false guard.** `trustedHostSlotCount < 2` cannot fire in this build because `DefaultParallelAcceptanceCapacity == BuildConcurrencySlotCount == 2` (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorBatchLoop.cs:43-47,2650-2654`; `src/Mcg.AgentOrchestrator.Infrastructure/Workspaces/DotnetBuildEnvironmentManager.cs:93-95`).

**Fact, based on all three production construction call sites.** Invalid acceptance-slot settings cannot arise through current production wiring: the public constructor fixes the getter to the constant (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorDriver.cs:239-247`), and the app's conductor and background-attempt paths all use that constructor (`src/Mcg.AgentOrchestrator.App/Cli/CliCommandHandlers.Goals.cs:1435-1447,1725-1737`; `src/Mcg.AgentOrchestrator.App/Orchestration/ConductorParallelAcceptanceAttempts.cs:965-984`). The invalid-settings branch remains reachable through the internal injectable test constructor; it is production-dead, not universally dead.

**Fact — stale invariant/comment.** The capacity comment says every running gate holds a build slot and uses that as the reason to tie parallel-acceptance width to build concurrency (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorBatchLoop.cs:43-47`). That is no longer true across the shard phase because the verifier releases the execution lock immediately after successful prebuild (`src/Mcg.AgentOrchestrator.Infrastructure/Workspaces/GoalAcceptanceVerifier.cs:1232-1245`). The constants remain numerically coupled, but the receipt proves the physical permit was free from 00:18:09 while the gate remained logically active until 00:33:24 (`.orchestrator/logs/conduct-events.log:24,192-193`).

**Unknown.** Source and the supplied/durable records establish the blocking ownership key, but they do not establish why the product policy needs to serialize every acceptance gate that touches different files in the same test project for the gate's entire post-prebuild lifetime. That would require an invariant or failure receipt demonstrating unsafe cross-goal shard overlap for this ownership key; none is read by `activeCandidates.Overlaps`, which only compares normalized write-set metadata (`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorParallelAcceptance.cs:19-27`). The code therefore supports the diagnosis “this policy bound,” not the stronger conclusion “this serialization is necessary.”
