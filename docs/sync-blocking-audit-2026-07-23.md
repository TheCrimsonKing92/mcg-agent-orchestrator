# Sync Blocking Audit

Audit date: 2026-07-23

## Principle Statement

Long-running, dispatch-bound, or externally-dependent work -- AI/worker dispatches, subprocess runs (codex/dotnet/git), network/HTTP calls, sleeps/poll-waits, or any operation whose duration is unbounded or seconds-to-minutes -- must be ENQUEUED and driven by EVENTS/state-transitions, never executed INLINE while (a) holding a shared lock (the state.db write path, a build/testhost slot or lease, a global mutex/semaphore) or (b) blocking an operator-facing synchronous command's thread. Correct shape: acquire lock -> fast durable write (enqueue/record) -> release; run the slow work outside the lock; surface progress/completion via state transitions and events, not by the submitter waiting.

## Audit Method

Repository-wide production C# scan used co-occurrence searches for transaction/lock/lease scopes and slow calls (`BeginTransaction`, `TransactAsync`, `SemaphoreSlim`, `lock (`, lease acquisition, `Process.Start`, `WaitForExit`, `WaitForExitAsync`, `CompleteAsync`, `HttpClient`, `Task.Delay`, `Thread.Sleep`, `.GetResult`). Tests and generated output were excluded from production findings. High-risk hits were traced through call chains until both the held resource boundary and the slow operation were identified.

## Coverage

### Deeply Audited

- CLI persistent state routing: `CliPersistentStateRunner`, `CliCommandHandlers.Goals*`, `CliCommandHandlers.Tasks`, `CliCommandHandlers.Workers`, `RunGoalService`, and `GoalEventsCommand`. Reason: generic CLI transaction scope is the known trigger surface and hosts operator-facing commands.
- Goal refinement and model execution: `GoalLifecycleCommands`, `GoalRefinementGate`, `GoalRefinementService`, and `AgentTaskRunner`. Reason: AI/model calls are the slow operation in the seeded violation and dashboard/API paths.
- Dashboard mutation paths: `DashboardEndpointServices`, `DashboardEndpoints.Goals`, and `GoalManagementCommandService.*`. Reason: dashboard mutations combine a semaphore, transactional state wrapper, and user-facing HTTP handlers.
- Dispatch/process start and verification: `BackgroundDispatchRunner`, `LocalProcessVerifier`, and `WorkerProcessRunner`. Reason: subprocess launch and wait boundaries are the main completion-coupled operations.
- Acceptance/conductor landing: `GoalAcceptanceVerifier`, `ConductorDriver`, `ConductorBatchLoop`, `ConductorParallelAcceptanceAttempts`, and `DotnetBuildEnvironmentManager`. Reason: acceptance uses scarce build/test slots and can run from operator and loop paths.

### Scanned

- Persistence stores other than orchestrator state (`BacklogStore`, `CollaborationItemStore`, `DogfoodLogStore`, `RunEventStore`, `PortfolioStore`, `ProgressiveReviewSteeringStore`). Reason: searches found short transaction/busy-retry mechanics but not verified transaction scopes spanning dispatch/model/process/network completion.
- Operator communications (`DiscordGatewayListener`, `DiscordControlPlaneDeliverer`, message transports, dead-man heartbeat, steward dispatcher). Reason: network calls were found, but no state transaction or global mutation gate was verified around the HTTP/Discord calls in this pass.
- Remote git mirror and worktree helpers. Reason: process/git calls are present, but the primary mirror worker is backgrounded and no state.db write transaction was verified across remote push completion in this pass.
- Provider registry and smoke checks. Reason: synchronous HTTP probes exist, but they are startup/diagnostic checks rather than mutation-gated submission/completion paths.
- Dashboard monitoring streams. Reason: polling loops are explicit streaming/read surfaces and were not found holding dashboard mutation state.

### Not Audited

- Tests under `tests/`. Reason: excluded from production violation findings per scope; real-process test concerns belong to `docs/test-design-audit.md`.
- Generated outputs and runtime state (`bin/`, `obj/`, `.scratch`, `.orchestrator-prototype`, `TestResults`, logs). Reason: not source and excluded by repository guidance.
- Scripts outside production C# source. Reason: this pass focused on production C# paths where state transactions, dispatches, and dashboard/API handlers are implemented.
- Runtime dashboard/orchestrator state. Reason: the task explicitly prohibited dashboard APIs and orchestrator state access; this is a static code audit only.

## Proposed Guidance Insertion

Exact proposed anchor name: `decouple-submission-from-completion`

Proposed markdown for `AGENTS.md` and the counterpart `CLAUDE.md` shared-discipline block:

```markdown
<!-- shared-discipline:decouple-submission-from-completion -->
## Decouple Submission From Completion

Long-running, dispatch-bound, or externally-dependent work -- AI/worker dispatches, subprocess runs, network calls, sleeps/poll-waits, or operations with seconds-to-minutes duration -- must not run inline while holding `state.db` write access, a build/testhost slot or lease, a global mutex/semaphore, or an operator-facing synchronous command thread.

Correct shape: acquire the shared resource only long enough to durably record intent, enqueue work, or checkpoint state; release it; run the slow work from an event-driven owner; persist progress/completion through state transitions and observable events. If a command needs to wait for completion, it should observe those events rather than owning the work while a shared resource remains held.
```

This insertion was not applied in this goal because the deliverable is analysis-only and the working tree must contain only the new audit report.

## Prioritized Follow-on Goals

1. Async goal intake and refinement queue. Scope: make `goal`, `simple-goal`, backlog-created goals, and dashboard refinement gates record refinement intent and return without running the refiner under a state transaction. Affected files: `CliPersistentStateRunner.cs`, `CliCommandHandlers.Goals*.cs`, `GoalLifecycleCommands.cs`, `GoalRefinementGate.cs`, `GoalRefinementService.cs`, `DashboardEndpoints.Goals.cs`, `GoalManagementCommandService.TaskActions.cs`. Depends on: async-intake goal.
2. Eventful task execution and verification intents. Scope: convert CLI/dashboard `run`, `api-run`, and `verify` to durable request records processed by background executors with task progress/verification events. Affected files: `CliCommandHandlers.Tasks.cs`, `DashboardEndpointServices.cs`, `DashboardEndpoints.Goals.cs`, `GoalManagementCommandService.TaskActions.cs`, `GoalManagementCommandService.Advancement.cs`, `AgentTaskRunner.cs`, `LocalProcessVerifier.cs`. Depends on: none.
3. Eventful dispatch start intents. Scope: split dispatch preparation from process launch so `start-dispatch`, `start-dispatches`, dashboard start controls, and conductor start decisions persist intent before an external process host is spawned. Affected files: `CliCommandHandlers.Workers.cs`, `GoalManagementCommandService.Dispatches.cs`, `GoalManagementCommandService.Advancement.cs`, `BackgroundDispatchRunner.cs`, `ConductorDriver.cs`. Depends on: none.
4. Eventful acceptance gate worker. Scope: turn acceptance into admission plus background gate attempts with lease ownership, heartbeat, terminal artifact reconciliation, and nonblocking operator/conductor observation. Affected files: `CliCommandHandlers.Goals.Acceptance.cs`, `ConductorDriver.cs`, `ConductorBatchLoop.cs`, `ConductorParallelAcceptanceAttempts.cs`, `GoalAcceptanceVerifier.cs`, `DotnetBuildEnvironmentManager.cs`. Depends on: none.
5. Async conductor observability forwarding. Scope: keep tick persistence local and move dashboard HTTP POSTs to a separate forwarder so slow dashboard I/O cannot stall conduct ticks. Affected files: `ConductorBatchLoop.cs`, `ConductorTickPusher.cs`, `CliCommandHandlers.Goals.cs`, dashboard tick endpoints. Depends on: none.
