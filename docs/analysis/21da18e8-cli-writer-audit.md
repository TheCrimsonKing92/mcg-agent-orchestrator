Scope: brief v4's bounded writer-family correction plus the original graph-repair feature. These are source findings, not execution receipts or a diagnosis of the August incident. Reviewer must independently check the exclusions against the final candidate.

## Corrected owners

`ExecuteBacklogIntakeOutsideTransaction` captures all load-time goal baselines. `ExecuteAcceptanceQueueOutsideTransaction` reuses its existing `initialGoalSnapshots`. Both supply `CreateCommandCheckpoint` for intermediate and final saves. That adapter derives the changed set from the complete kernel plus human requests, submits existing goals individually to `SaveGoalSnapshotsWithMergeAsync`, advances each durable baseline, and uses `RebaseCheckpointAfterDurableSave` after merges/skips. Unchanged loaded goals are never submitted.

New goals use `CommitGoalCreationAsync` → `TransactGoalCreationWithOutboxAsync`, including the existing precondition/claim validator. Absent rows are never sent to merge-save. `PersistBacklogIntakeGoal` continues to mark the reservation only after its checkpoint returns. No `HasGoalCreationFinalizer` behavior flag changes. Batch commits are independent; failure reports committed goal ids, and the failed creation's state/outbox/claim transaction rolls back. Reservation recovery stays with BacklogIntakeRecordStore.

Conflict policy for both corrected callers is merge-with-loud-skip. Independent progress may merge; `Skipped` is an exception, with submitted/stored state in exception data and committed/uncommitted identities in the diagnostic. The adapter rebases before throwing, so a caught rejection cannot replay an obsolete kernel. It never retries or falls back to raw save. Acceptance's existing `GoalOperationJournal.AcceptanceGatePassed` writes candidate-bound passing evidence before merge/checkpoint; rejection does not delete that journal. Existing admission-critical checkpoints retain their separate RejectConflict policy.

## Acceptance caller correction

`ExecuteAcceptanceOutsideTransaction` constructs one `CliAcceptanceCheckpoint` before its sweep. Its `_baselines` map starts from `initialGoalSnapshot`; the progress adapter, critical RejectConflict saves and `recordDurableGoalBaseline` share it. Human baselines are captured before the sweep too, so request-only sweep changes remain detectable. Progress saves advance and rebase that same owner. The full dispatcher reload records non-target states as read-only observations, never owned baselines. Before any progress or critical write the collaborator rejects changed non-target state/requests; only a target projection reaches the checkpoint owner, so an unrelated row cannot become an accidental creation. Human requests for the target accompany that projection.

The existing `CreateCommandCheckpoint` adapter is extracted into `CliCommandCheckpoint` with the original runner factory retained. Its saves still use the same repository merge and `CommitGoalCreationAsync` owners; the latter becomes internal for this collaborator. This is code extraction, not a new persistence authority. The runner remains within the existing 4,786-line file and 5,955-line/18-partial ceilings; none are raised.

Preflight repairs and `Finalize` remain independent store-side progress, not checkpoint baseline advancement. After a non-aborted Finalize and dispatcher return, the final checkpoint merges the handler's target delta against that shared baseline. `RecordAcceptanceCompleted` also completes the local goal, so `TryMergeGoalSnapshots`/`PickTickOwned` retains Completed; `MergeTimeline` retains both durable finalization and later backlog/cleanup notes. Replacing the local goal with Finalize's earlier snapshot would discard those later notes, as reported by `PersistentRunnerAcceptanceJournalsBacklogCloseNoopAndPersistsMissingWarning` on candidate `5ff4404d`. The standalone failed-gate path retains Verified plus its candidate-bound `LatestAcceptanceFailure`; conductor failure routing is a separate transition. Existing merge guards, critical RejectConflict, rejection suppression and the durable gate journal remain in place. Native execution of this correction remains Acceptance-owned.

Conflict policy remains merge-with-loud-skip. In particular, `SqliteOrchestratorStateRepository.cs::TryMergeTaskSnapshots`, the `!hasCurrent` branch, rejects a new store-only task rather than incorporating it. The acceptance caller must report that skipped intended mutation with stored/submitted evidence, preserving the graph and its external journal. A passing gate with any concurrent task-set change is still guarded from landing by `AcceptanceMergeGuard.Compare`; compatibility with worker ownership does not waive acceptance's candidate guard. A normal passing merge with independent task notes must retain Completed, notes and candidate-paired gate-passed/passed journal entries. Tests are authored, not executed.

`CliCommandTestsPersistentRunnerCommandsGraphRepair` uses an event-gated actual acceptance verifier and real SQLite. It covers passing/failing verdicts with independent notes, compatible append with guarded abort or loud skip, other-goal request equality, and a predecessor change causing guarded landing rejection. That predecessor case seeds the store directly to challenge the acceptance guard; it does **not** prove the typed graph-repair compatibility validator. Supporting tests exercise the same invocation-scoped checkpoint collaborator for progress followed by strict persistence, and reject non-target graph or request-only changes before even the target saves. `CliCommandTestsGraphRepairConductCheckpoint` now authors the actual single-goal watch caller: pause after a real progress save, commit an unrelated request, then require the subsequent native critical checkpoint baseline to match that invocation's durable state. Its supported stop and deliberate final rejection prevent a fixture worker from starting. Execution remains Acceptance-owned.

## v4 implementation and pending verification

The three named families now construct `CliOwnedGoalCheckpoint` before sweep computation or external work. Its baseline contains both goal and requests. The complete changed set is validated before the first write: absent baselines, removed observations, orphan requests and non-target changes fail without saving the target. There is no creation fallback. Existing repository merge handles non-terminal progress; terminal snapshots use RejectConflict. Every skipped intended mutation is explicit, with submitted/stored/baseline evidence. Durable outcomes rebase the kernel and advance the same invocation baseline, including requests, so subsequent checkpoints cannot replay the prior kernel or conflict with their own save.

Startup captures after loading its sweep kernel and before calling TerminalGoalSweep. Its per-goal callback surfaces a conflict through CollaborationItemStore, with submitted/stored snapshots, and continues the other goals. It evaluates all goal/request changes, not just `sweep.Changed` or a target id. Journals remain intact. Mark-landed still records landing intent, land/record operations and terminal disposition before its checkpoint; a rejection cannot erase that external-work evidence.

New landing intents and terminal dispositions bind `TaskGraphIdentity`: ordered existing task identities, roles and descriptions, independent of progress. TerminalGoalSweep checks both bindings before recovery and reports `landing-graph-changed` rather than closing uncovered appended tasks. Mark-landed cannot replace that old binding with a different graph merely by replaying the command. Historical unbound landing records retain their existing compatibility behavior; no graph-coverage proof is inferred from those legacy records. This guard is required for new conflicting writes produced by this candidate, and does not claim migration of historical evidence.

`CliWriterPersistenceBoundaryTests` walks compiler-emitted method operands for every App method, including generated callbacks, requiring zero production references to the legacy captured-goal replacement sink. A compiled counterexample checks the guard's sensitivity. This is a reference invariant, not a fixed caller census. Handler-based generic-writer exclusions above remain necessary, because its raw SaveAsync branch intentionally remains unchanged.

`CliCommandTestsGraphRepairWriterFamilies` authors actual-runner interleavings for startup, readiness-repair, goal-recovery, next, supervisor --apply-safe and mark-landed. It includes authoritative append survival, explicit rejection, goal-local startup continuation, unrelated goal/request equality, same-graph recovery versus uncovered-graph refusal, and repeated/request-only/scoped checkpoint behavior. All test execution, compiling negative controls and independent combined-candidate review remain pending with Acceptance/Reviewer. No runtime reproduction or contention claim is made.

## Original admission boundary and resolved authorization

Source: `Execution/Persistence/TaskIntentAdmission.cs::Serialize` keys the existing mutex by store + goal + task and immediately executes without locking for a null task target. `Launch` holds that mutex around suppression, native start and launch acknowledgment. `OperatorIntentStore.cs::EnqueueAsync` uses the same method; a goal-only repair therefore bypasses the existing synchronization. Admission revisions/preparations are task-specific, and `GoalDispatchOperationsStart` consults those references. A final unprotected graph read would leave the acknowledged-repair/check-to-start race open.

The operator authorized goal scope in the existing TaskIntentAdmission helper, without another lock type, lease, table or transaction owner. Goal-only enqueue and compatibility/application take its goal key. Native Launch/ExecuteAuthorized take goal then the existing task key; task intake retains its task key and never requests a goal key while holding it. Pending/claimed repair fences launch through graph persistence and recoverable outcome completion; completion follows the existing typed application marker protocol. Preparations bind an ordered graph fingerprint in the existing preparation table (schema 3). Final admission checks that binding against authoritative persisted state while still owning both keys. All four CaptureAdmission production call sites now supply the binding. Unrelated goals have different mutex keys.

`CliTaskGraphRepairCommand` is an early inbox-only persistent route, before state outbox draining. The in-memory dispatcher uses that same submission helper and returns false, so neither CLI route directly inserts. `TaskGraphRepair.Apply` validates the complete progressively simulated plan before any AddTask call; it checks durable native launch ownership as well as current task state. Generated pre-review guidance says to poll application before re-evaluation. Bare replay uses canonical contents plus goal id; paths and graph versions are excluded. Explicit keys retain the store's complete-request/attribution comparison.

The original persistence-family corrections remain prerequisites, not a separately accepted landing. Candidate builds, actual native tests/negative controls, independent combined-candidate review and Operator live proof remain separate evidence obligations. No historical runtime cause is asserted.

The single-goal watch dispatcher now wires `persistGoalKernel` to the same `CliAcceptanceCheckpoint.PersistGoals` owner as normal/critical saves. The former unset callback could acknowledge progress without persisting it in this caller. Scope validation occurs before any target save; no new baseline or creation authority is introduced. Compiler-reference coverage in `CliWriterPersistenceBoundaryTests.Candidate_CliCannotDirectlyInsertTasks` checks the App assembly's actual references to both kernel insertion entrypoints, including generated callbacks, with a compiled bypass counterexample. This complements the existing captured-replacement guard and handler exclusions.

Existing owned-worker build actions retain task-intent authorization under goal-before-task serialization; compatible graph repair does not invalidate them. Only new native worker admission enforces the graph/repair fence. `GraphRepairAdmissionTests.AdmittedWorker_RejectsNewPredecessor_AllowsCompatibleAppend_AndCompletesOriginalIdentity` covers the process, its durable identity and those build actions across repair.

Compatibility also uses the existing dispatch-stage prerequisite rule, extracted without changing its role mapping into `SdlcTaskDependencies` and reused by `DispatchReadinessRules`. Appending a new earlier-stage role can add a prerequisite to an owned task even without a positional predecessor; repair rejects that too. A compatible append reopens Verified to Active while preserving completed task identities and lifecycle holds. After checkpoint rejection/rebase removes an uncommitted repair marker, the coordinator discards only its corresponding in-memory pending completion and resumes the existing claim/expiry path. It does not create a retry or withdraw protocol; the admission expiry remains bounded.
