`src/Mcg.AgentOrchestrator.App/Orchestration/ConductorParallelAcceptanceAttempts.cs::ConductorParallelAcceptanceAttempt` records branch and main head SHAs, owner process ID, scope paths, policy JSON, execution protocol and lease receipts. These records provide custody and recovery evidence, but do not bind a verdict to a complete trusted environment and an exact prospective landing tree.

Existing identity seams are `src/Mcg.AgentOrchestrator.Infrastructure/Workspaces/GoalAcceptanceVerifier.cs::ComputeEffectiveAcceptancePlanIdentity` and `src/Mcg.AgentOrchestrator.Infrastructure/Workspaces/GoalAcceptanceVerifier.cs::ComputeEffectiveAcceptanceManifestIdentity`. `src/Mcg.AgentOrchestrator.Infrastructure/Workspaces/AcceptancePartitionVerdictCache.cs::TryBuildCacheKey` combines goal, candidate tree, main SHA, manifest identity and filter hash. The verifier resolves the tested worktree's `HEAD^{tree}` for that cache; this is not an attestation that the eventual landed tree is identical. Preserve deterministic required checks and evidence custody when replacing execution.

## Acceptance envelope

The envelope is a versioned canonical byte representation with a SHA-256 content digest. Values must identify the complete trusted gate environment, not merely candidate-controlled configuration. **Fact:** the middle column identifies current partial inputs; **design:** the final column specifies additional work. “not computed” means the required envelope value is absent, even where related inputs exist.

| Field | Where its value is computed today | Work needed to produce it |
| --- | --- | --- |
| Candidate commit | `src/Mcg.AgentOrchestrator.App/Orchestration/ConductorParallelAcceptanceAttempts.cs::ConductorParallelAcceptanceAttempt` carries branch head SHA. | Resolve a full immutable commit identity and repository identity; for grouped work retain the synthetic candidate and ordered member commits. Reject unresolved identities for protocol use. |
| Exact prospective landing-tree hash | not computed | Materialize the exact prospective integration result against an immutable main revision without updating landing refs; record its Git tree hash and export those bytes as source. A tested candidate tree or grouped revision alone is insufficient. Recompute when main or the integration strategy changes and compare again at landing. |
| Trusted gate-policy digest | not computed | Canonicalize policy from an operator-approved trust root outside candidate authority; hash policy, gate executable and transitive scripts/configuration that determine execution. Validate schema and identity before accepting a verdict; capture claims from the runner separately from trusted supervisor observations. |

Current trust seams are `src/Mcg.AgentOrchestrator.Infrastructure/Workspaces/AcceptanceGateEngineSettings.cs::Load`, which reads `config/acceptance-manifest.json` in the worktree, and `src/Mcg.AgentOrchestrator.Infrastructure/Workspaces/GoalAcceptanceVerifier.OwnerProtectedFingerprint.cs::ComputeOwnerProtectedChangeFingerprintForCandidate`. Inbox re-entry is idempotent on **(repository, goal, candidate SHA, landing-tree hash, gate-policy digest, attempt)**. Each entry additionally binds the envelope digest; a duplicate with different content is a protocol error, never a cached pass. A fresh attempt identifier is required for a retry; caches can only reuse evidence matching the entire trusted environment and tree. Validate receipt contents, producer authority and attempt lifetime atomically when consuming them. A PID alone, an artifact path or a successful exit code is not attestation.

## Shadow run and promotion

The following numbers are the proposed operating rule for this design, pending owner ratification. Shadow execution and pair production are later work, dependent on the first slice's envelope corpus. Before promotion the existing gate retains landing authority; the runner is advisory only.

A **pair** is the existing gate verdict and runner verdict for the same byte-identical envelope digest, prospective landing tree, policy and required checks. A legacy run qualifies only if its recorded effective environment matches the envelope; an annotation on an uncontrolled legacy run is insufficient. Normalize verdicts to pass/fail on required checks, retaining diagnostics and per-check evidence. Exclude attempts missing either verdict from paired disagreement, but count runner failures in the infrastructure denominator; zero valid pairs cannot satisfy promotion.

- **Disagreement rate:** number of pairs with different pass/fail verdicts divided by pairs with both verdicts, multiplied by 100.
- **Infrastructure-failure rate:** runner attempts without a valid verdict due to startup, unavailable isolation, supervisor limit termination, export failure, or missing/malformed/identity-mismatched evidence, divided by all runner attempts, multiplied by 100. A completed required check's assertion failure is a fail verdict, not infrastructure failure. Rejected/unavailable starts count as attempts; retries do not erase failures.
- **Minimum sample:** at least **200** distinct complete pairs across at least **20** distinct goals, covering per-goal, cohort, merge-train and recovery/adoption paths in the scope to be promoted; at least **10** pairs for each of those four paths. Include at least **20** controlled failing candidates to exercise rejection, without permitting them to land. Repeated delivery of the same attempt counts once.
- **Promotion thresholds:** disagreement at most **1.0%** (at most **2** of exactly **200** complete pairs), **0** runner-pass/existing-gate-fail pairs, and infrastructure failures at most **2.0%** of all runner attempts (at most **4** of exactly **200** attempts). Infrastructure attempts and complete pairs have different denominators; report both counts. Apply the percentages to the whole qualifying sample, not a selected subset.
- **Promotion rule:** all thresholds and coverage requirements must hold for one policy/environment/backend version; every disagreement must have a documented resolution, and the Operator must explicitly approve the scope and receipts. A gate-policy, manifest, toolchain, limit, evidence-schema or backend version change restarts that scope's sample. Rates measure this sample, not a statistical guarantee about every future failure.

Runner unavailability is reported as diagnostics and **never authorizes a landing**. Before promotion, only independently sufficient current-gate evidence can authorize one. After promotion, acceptance authority transfers to the runner for the promoted scope: unavailable isolation, invalid evidence, or a changed landing tree blocks landing, with **no downgrade fallback** to the old execution path. A changed tree requires a new envelope and verdict; conductor recovery can re-enter the inbox but cannot relax validation.

## First implementation slice

### Goal brief: record acceptance envelopes alongside current verdicts

**Objective:** compute and record all eleven envelope fields and their canonical digest for each gate attempt, including the prospective landing-tree hash, alongside existing verdict artifacts. This is an observation-only slice: no runner process, landing authority transfer, host provisioning or paired execution is introduced. The envelope is not read by landing decision paths. Successful records form a corpus for later protocol work; they are not qualifying shadow pairs or proof of isolation.

**Owning seams:** extend attempt creation/persistence in `src/Mcg.AgentOrchestrator.App/Orchestration/ConductorParallelAcceptanceAttempts.cs::ConductorParallelAcceptanceAttemptCoordinator` and `src/Mcg.AgentOrchestrator.App/Orchestration/ConductorGroupedGateAttempts.cs::ConductorGroupedGateAttemptCoordinator`, and preserve records through `src/Mcg.AgentOrchestrator.App/Orchestration/ConductorOrphanGateAttemptAdoption.cs::ConductorOrphanGateAttemptAdoption`. Reuse effective-plan identities from the verifier. Keep canonical envelope data with its attempt, and terminal envelope status with the current result, rather than creating another mutable registry.

**Contract and lifecycle:** snapshot immutable candidate/main inputs and the exact prospective integration tree at attempt creation, using the conductor's integration strategy without writing refs. A conflict produces a typed diagnostic rather than an invented tree. Record trusted policy provenance, resolved toolchain hashes, explicit desired limits and evidence-schema version; separately label what the legacy gate actually enforces. Hash the canonical intended envelope and preserve it unchanged through completion/adoption. Bind observations and enforcement gaps as separate receipts. If a required value cannot be produced, persist a typed recording failure with the missing field and source; do not emit a usable envelope digest or silently preserve a stale one. Recording failures remain visible diagnostics and do not alter current landing decisions. Later authority-bearing work must reject such records.

**Acceptance criteria and required evidence** (ownership follows `docs/role-capability-matrix.md`; every criterion is TEST-VERIFIABLE):

- Each per-goal, cohort and merge-train attempt persists the versioned eleven-field envelope, digest, repository/goal/attempt identities and pinned candidate/main inputs, or an explicit recording-failure status; adoption retains original identity without recomputation under a successor's ambient state. Evidence: round-trip/adoption fixtures and a source trace of all creation paths. Developer owns; Acceptance executes. `evidence_owner=acceptance-gate`.
- Prospective-tree fixtures cover unchanged main, conflict-free divergence, conflict and grouped integration; recomputing the selected integration produces the recorded tree, and changed main produces a different recording or a typed diagnostic. No fixture updates landing refs. Evidence: deterministic integration fixtures. Developer owns; Acceptance executes. `evidence_owner=acceptance-gate`.
- Canonicalization gives identical digests for equivalent inputs and different digests for each changed policy, manifest, required check, toolchain, limit or schema input; unresolved provenance/toolchain values produce explicit recording failure rather than a usable digest. Desired limits and observed enforcement are distinguishable. Evidence: identity and missing-input fixtures. Developer owns; Acceptance executes. `evidence_owner=acceptance-gate`.
- Duplicate delivery of the same inbox key/envelope preserves one recording; differing content under the same key is a typed recording error, and partial writes or stale evidence cannot become a successful recording. Evidence: persistence and recovery fixtures. Developer owns; Acceptance executes. `evidence_owner=acceptance-gate`.
- No landing decision consumes the envelope or its status, and no new runner launch, host setting, network permission or fallback path is introduced. Evidence: Reviewer inspects callers and the scoped diff, comparing decision inputs with the pre-change source. Developer owns; Reviewer executes. `evidence_owner=worker`.
- Injected recording failures leave legacy pass/fail, retry, adoption and landing eligibility unchanged while exposing the failure in diagnostics; existing decision paths remain covered unmodified. Evidence: focused regression and fault-injection receipts requested by Tester and executed by Acceptance. Developer owns; Acceptance executes. `evidence_owner=acceptance-gate`.

**Stop conditions:** stop this slice if it requires changing landing authority, granting host privileges, implementing runner execution, or weakening a required check. Report unresolved inputs through the recording contract, and route test execution to Acceptance. Subsequent goals own isolation backend qualification, trusted evidence export, inbox consumption and measured shadow pairing.
