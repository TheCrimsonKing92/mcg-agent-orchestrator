- **In-tree build lock blocks rebuild/restart while any orchestrator process runs** (item 606910bb — concrete design 2026-06-18). Every orchestrator process — the launcher's `dotnet App.dll`, `conduct --loop`/`--watch`, `operator-listen`, `serve-dashboard`, and each `dotnet App.dll __dispatch-run` worker host — runs from `src/…/App/bin/Debug/net10.0` and loads `Core.dll`/`Infrastructure.dll` from there, locking them. A later `dotnet build` then can't copy fresh deps into App's bin (MSB3027), so nothing rebuilds while ANY orchestrator process runs. Hit repeatedly 2026-06-18: a 30-min Developer dispatch host alone blocks restarting the loop/listener on a fresh build, and even one source edit makes the next launcher invocation fail to rebuild.
  - Fix: run long-running processes from a COPY of the App bin, not the in-tree bin, so in-tree stays free for rebuilds. (a) Launcher snapshots App's bin to a per-invocation run-dir and runs `dotnet <run-dir>/App.dll` for the long-running subcommands (`conduct --loop/--watch`, `operator-listen`, `serve-dashboard`); short commands can stay in-tree (brief lock). (b) The dispatch-host spawn (`BackgroundDispatchRunner`) copies App + deps to a per-dispatch run-dir and spawns from there.
  - Subtleties: a detached dispatch host OUTLIVES its spawner, so it needs its OWN run-dir (cleaning the spawner's would yank the host's DLLs mid-run). Reap run-dirs on startup, skipping any whose owning process is still alive. Copy cost ~tens of MB / ~1s per long-running launch — fine; skip it for short commands.
  - Acceptance: with a dispatch-host worker running, `dotnet build` + a loop/listener restart on the fresh binary both succeed (no MSB3027); run-dirs don't accumulate unbounded.

- **OS-level worker sandbox: confine codex writes to the worktree without codex's broken Windows sandbox** (design 2026-06-19, building now). PROBLEM: codex's `--sandbox workspace-write` is the only enforced write-confinement, but on Windows it poisons the session under `dotnet build/test` load — `CreateProcessAsUserW failed: 5` (ERROR_ACCESS_DENIED) on every subsequent launch, instantly, so the worker does the work but can't `git commit`. `--sandbox danger-full-access` dodges the bug but removes ALL isolation (Miles requires TRUE worktree isolation). Two independent expert assessments (Opus + codex gpt-5.5 xhigh, web-checked MS/Linux docs) CONVERGED on the same fix.
  - DESIGN (dedicated-user + ACL, Windows): run the worker as a dedicated low-priv local user (`mcg-worker`, created once via `scripts/Setup-WorkerSandbox.ps1`, password in Credential Manager `mcg-orchestrator-worker`). It's a separate standard-user profile → by default cannot write the operator's profile (the repo) or system. At dispatch, the orchestrator (owner of the worktree dirs) grants `mcg-worker` Modify on the per-run **sandbox root only**, then launches codex `--sandbox danger-full-access` AS that user. KEY PRINCIPLE both experts stressed: set the boundary ONCE at the root; children (`dotnet`/MSBuild/testhost/git/pwsh) inherit the standard-user token via ORDINARY `CreateProcess` → no per-spawn restricted token → codex's `CreateProcessAsUserW` poisoning never happens (to dotnet it's a normal standard-user session). Job object `KILL_ON_JOB_CLOSE` for cleanup only, NOT security.
  - WRITABLE SET (codex's sharp catch): a plain worktree is NOT enough — git writes worktree metadata to the COMMON `.git` (objects/refs, `.git/worktrees/<name>`) OUTSIDE the worktree. So grant write on worktree + the git common dir (or use a per-run self-contained clone) + a scratch/temp/NuGet area; everything else default-denies. "Isolated to the worktree" honestly = isolated to a per-run sandbox ROOT containing those.
  - INTEGRATION POINTS: launch is `DispatchProcessHost.cs:111` (`ProcessStartInfo` → add `UserName`/`Password`/`Domain="."` from config+CredRead when sandbox enabled; redirected stdout/stderr use handles the host opened AS the operator, so logs sidestep `mcg-worker`'s ACLs — verified by reading the launch). Carry the sandbox account + writable-set in `DispatchRunParameters` (set by `BackgroundDispatchRunner.StartLatestDispatch`). Switch `WorkerProfileDispatcher.BuildDispatchVariables` `{sandboxMode}` → `danger-full-access` ONLY when the OS sandbox is active (else keep `workspace-write`). SUBTLETY to validate against the real account: a `CreateProcessWithLogonW`-launched process needs window-station/desktop access granted to the worker SID + profile-load + handle inheritance across the logon boundary — the fiddly part, build with validation, not blind.
  - CROSS-PLATFORM: unified ABSTRACTION (read-only roots, writable sandbox root, scratch, env, cleanup), divergent backends — Windows = user+ACL; Linux = bubblewrap (ro-bind `/` + writable bind for the sandbox root; Anthropic's own sandbox-runtime does exactly this) + optional Landlock.
  - DE-RISK (both experts' identical first experiment, run for real once `mcg-worker` exists): launch codex full-access AS `mcg-worker` under the ACLs, run `dotnet build` + `dotnet test` + a trivial `pwsh -NoProfile -Command "Write-Output ok"` AFTER the burst — assert (a) the trivial command still works (no poisoning → we shed codex's fragility) AND (b) writes to the main repo / `C:\Users\Public` / the parent `.git` are ACL-denied while writes inside the sandbox root succeed.
  - Acceptance: a codex Developer/Tester dispatch on Windows completes AND commits (no `CreateProcessAsUserW` poisoning), and an attempted write outside the sandbox root is OS-denied. Supersedes the `workspace-write` + orchestrator-recovery fallback.
