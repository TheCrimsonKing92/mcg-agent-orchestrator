## Spike a Claude Agent SDK worker harness for the Anthropic lane

Today the Anthropic worker lane shells out to `claude --model ... -p (Get-Content prompt)` and treats stdout as an opaque blob. `claude -p` buffers all output until completion, so the orchestrator cannot see progress (0 stdout looks identical to a hang - this caused a working worker to be cancelled at a 20-min wait cap on 2026-06-13), and the `WORKER_RESULT` contract plus the commit convention are prose the model may ignore (spark failed both ways; weak/cheap/local models fail this class consistently). The fix is to drive the inner loop through a harness we control instead of a buffered CLI. Key enabler (verified 2026-06-13 via the claude-api skill): the Claude Agent SDK resolves credentials the same way Claude Code does, including an `ant auth login` OAuth subscription profile - so an SDK-based harness keeps the subscription budget and does NOT force paid per-token API billing. Scope: behind the existing worker-profile abstraction (`WorkerProfileDispatcher`/`WorkerProfiles`), add an Agent-SDK-backed dispatch path for one Anthropic role first; capture changed files / commands / commit sha deterministically from SDK events rather than parsing a model-emitted block, stream progress events so stall detection keys on real activity (not stdout bytes - see [[worker-dispatch-monitoring]]), and enforce commit/verification as loop steps or tool gates. Keep codex/qwen on the wrapped-CLI path (no equivalent subscription-preserving SDK; codex removed its chat wire API per the decision record) and keep the outer orchestrator (decomposition, worktree isolation, acceptance gates, routing, recovery) unchanged. Before building, confirm the Agent SDK hook surface (PreToolUse/PostToolUse/Stop) and auth-profile usage against the Agent SDK docs - the claude-api skill reference covers the Messages API and Managed Agents, not the local SDK's hook names. Done when one role dispatches through the SDK harness on the subscription profile, the dispatch record is populated from structured SDK events (not WORKER_RESULT prose), progress/stall is judged from streamed activity, and a comparison run (same task via `claude -p` vs the SDK harness) shows equal-or-better acceptance plus richer per-dispatch signal for the outcome scorecard; tests cover event-to-dispatch-record mapping, enforced-commit, and stall classification. Managed Agents (server-hosted, paid per-token) is a deliberately deferred alternative for specific high-value runs, not the default given the subscription-first posture.

## Generalize planners/brokers beyond the self-hosted .NET assumption

The dogfood loop has only ever targeted this repo, so self-hosting assumptions have leaked into logic meant to be repo-agnostic. Confirmed 2026-06-13 by pointing the orchestrator at an external repo (`net-health`, a .NET/WPF app) via `MCG_ORCHESTRATOR_REPOSITORY_ROOT`: the source-survey broker generalized well (excluded build artifacts, mapped a foreign WPF structure, read the target's `AGENTS.md`), but `GoalObjectivePlanner` emitted `requiredTools` containing the orchestrator's OWN `scripts/Invoke-IsolatedDotnet.ps1` - a path that does not exist in any other repo. Fix the concrete leak (objective-plan required-tools must be derived from the target repo / be generic, never hardcode orchestrator-local helper paths) and audit the other planners/brokers (test-impact selection, verification-policy compiler, acceptance `dotnet-test` defaults, build-lease manager) for hardcoded dotnet/Windows/self-repo assumptions. CONFIRMED on a non-.NET target (2026-06-13, probed `schema-drift`, a Go repo, read-only): (1) the **source survey is .NET-extension-biased** - it indexed only 13 files (scripts/workflows/testdata/README) and missed every `.go` file under `cmd/` and `internal/` (net-health's `.cs` got 134), so the source-extension filter must include Go/node/python/etc.; (2) the **verification/build/test scaffolding is hardcoded to .NET** - `deterministic-verification.md` and `workflow-brokers.md` instruct a Go worker to run `.\scripts\Invoke-IsolatedDotnet.ps1 ... test <project-or-sln>` and "avoid raw `dotnet test`", when Go needs `go test ./...`/`go build`. The fix is toolchain DETECTION (`go.mod`->Go, `package.json`->node, `.sln`/`.csproj`->dotnet) driving both the source-survey file filter and the build/test/verification command generation, degrading to a generic "run the project's tests" contract when unknown. Done when an objective plan + dispatch prep against an external repo contains no orchestrator-local paths, the source survey indexes the target language's source files, the acceptance/test/verification brokers emit toolchain-appropriate commands (or a generic contract) instead of assuming dotnet, and a read-only survey goal can be dispatched end-to-end against both a .NET and a non-.NET external repo with tests covering toolchain detection and artifact exclusion.

## Collapse the operator CLI to a small set of fundamentals composing to `next`

The CLI has grown to ~100 verbs (see the help banner in `Program.cs`), which is cognitive overload and the opposite of a coherent operator surface. Reduce the *operator-facing* surface to a handful of fundamentals while keeping the rest as internal/automation machinery (demote, do not delete - tests, dashboard, and automation depend on the existing verbs). Target fundamentals: `next [goal]` (the hub: observe state + recommend the single best action AND print the exact command to run it - it already aggregates next-action/triage/recovery/health/inbox, so fold status/monitor/readiness/evidence/stages/gates/verify-needed/input-needed/operator-inbox/subscription-plan/model-outcomes/failure-triage/goal-recovery/supervisor into it, with `next --full` for detail); `goal <objective>` (create work; flags `--simple`, `--from-backlog`, `--run` collapse goal/simple-goal/lifecycle-*/goal-plan/backlog-intake/intent-template/run-goal); `accept [goal]` (verify + merge + cleanup; folds acceptance/acceptance-queue/workspace merge+remove); `stop <goal> <reason> [--as cancel|park|rollback|abandon|supersede]` (folds the five disposal verbs); `config <agents|profiles|policy|doctor>` (folds agent/agent-add/worker-profile*/autonomy-policies/doctor); `dashboard [--mode local|hosted|read-only]` (folds the five dashboard-serving verbs). Demote ENTIRELY below the operator waterline (callable but never required - `next`/`goal --run` orchestrate them): the ~11 dispatch verbs (dispatch/worker-dispatch/profile-dispatch*/subscription-dispatch*/execute-dispatch/start-dispatch*/refresh-dispatch*/cancel-dispatch) and the cross-goal/drain start planners. Keep a small recovery set (`retry`, `note`, `answer`, `verify-manual`, `logs`) that `next` points to by printing the exact command, so the operator never memorizes them. Implementation: add thin alias verbs for the fundamentals over existing handlers, make `next` emit copy-pasteable exact commands for its recommendation, and reorganize the `Program.cs` help banner + README into "Fundamentals" vs "Advanced/Internal". Done when an operator can drive a full goal lifecycle (create -> run -> accept, with recovery) using only the fundamental verbs, `next` always prints the literal next command, the help banner shows ~6 fundamentals not ~100, and existing verbs/tests still pass unchanged.
